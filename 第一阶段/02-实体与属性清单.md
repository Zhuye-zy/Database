## 0. 依据来源（Step 0 提取）

1. **任务书（附件1）第二大类题目5**：以专利数据服务试验系统上“美国专利申请公布全文文本数据、美国专利授权公告全文文本数据、欧洲专利全文文本数据、EP专利摘要（DOCDB）数据”为研究对象，参考数据手册与样例数据，设计本地存储关系数据库。
2. **任务书总体要求**：后台数据库设计实现为主；**数据库不少于 20 个表**；尽可能体现键、外键，体现工作量/复杂度/难度/新颖性；第二大类“可以 AI 辅助，但必须注明哪些是 AI 的贡献”。
3. **任务分配2.md（A角色）**：获取数据资源 → 理解专利数据结构（INID 码、数据手册、样例解析）→ 识别实体与关系 → 绘制 ER 图 → 产出实体清单/关系分析/ER 图；设计提醒：多值属性拆表、引用自引用、专利族表、长文本 TEXT/LONGTEXT。
4. **教学大纲（2024级）**：需求分析阶段给出**用例图、数据流图、数据字典、E-R 图**；数据库规范化、定义基本表、完整性约束、索引等。
5. **报告模板**：报告摘要/分工 → 需求分析 → 方案设计（用例图、E-R图、流程图、伪代码、框图）→ 结果展示 → 小组总结。
6. **规范与官网依据**：WIPO ST.9（INID）、ST.3（国家码）、ST.16（文献种类码）、ST.36/ST.96（专利 XML）；**官网四类数据手册与样例**（US DTD v4.3/v4.4、EP `ep-patent-document-v1-4`、DOCDB `exchange-documents-v2.5.7`）；第三方 USPTO 样例 v4.6/v4.7 仅作版本差异对照；EPO PATSTAT/DOCDB 公开表结构作交叉验证。

## 2. 实体识别方法

1. 从四类官网样例 XML 的**元素路径**归纳出文档结构（US 申请 141、US 授权 262、EP 全文 190、DOCDB 92 条路径，见 XML 解析报告）；
2. 用 **INID 码**把著录项映射到业务概念（第 4 节映射表）；
3. 对每个候选实体做“**是否多值 / 是否长文本 / 是否有独立生命周期**”三问，决定建表或拆表；
4. 与 DOCDB/PATSTAT 表结构交叉验证字段命名与基数；
5. 统一用代理键（`*_id`）保证关联表稳定，同时保留业务唯一约束（如 `(publn_auth, publn_nr, publn_kind)`）。

## 3. 主键选型与多值属性处理

**主键选型原则**
1. **代理键优先**：核心实体用 `BIGINT` 自增 `*_id`，避免业务键变化（申请号/公布号格式各局不同）；对应 DOCDB 的 `appln_id/pat_publn_id` 也是代理键。
2. **业务唯一约束并列**：`patent(appln_auth, appln_nr, appln_kind)`、`publication(publn_auth, publn_nr, publn_kind)`、`person` 名称+国家等，保证“代理键之外可查重”。
3. **关联表用候选键作复合主键**：如 `patent_applicant(patent_id, sequence_nr)`；`sequence_nr` 在源文档内唯一定位一次角色出现，`person_id` 是该出现所指的外键。
4. **维表用自然码**：`country_office.ctry_code`、`language.lang_code`、`kind_code(office_code, kind_code)`，可读且稳定。
5. **自引用表**：`claim_dependency` 的依赖方/被依赖方均是 `claim.claim_id`，复合主键天然防重；`parent` 必须与 `dependent` 同属一份 `publication`（应用层或复合唯一约束保证）。
6. **各实体主键选型理由**：通用原则为“核心实体代理键（稳定、便于导入）+ 业务唯一约束（可查重）；维表用自然码（简洁、可读）；关联表用全复合主键（含联系属性）”。**每个实体的具体理由与多值处理方式已写在 §7 各实体小节的“主键选型理由/多值属性处理”两行**，例如 `classification(scheme_code, symbol)`、`claim(publication_id, lang_code, claim_number)`、`patent_family_member(member_id)`。

## 5. 长文本字段与类型建议

| 字段 | 类型建议（PostgreSQL） | MySQL 对应 | 理由 |
|---|---|---|---|
| `abstract.abstract_text` | `TEXT` | `LONGTEXT` | 摘要通常 200~2000 字符，EP 多语言翻倍；TEXT 无长度上限、避免 VARCHAR 截断 |
| `claim.claim_text` | `TEXT` | `LONGTEXT` | 单条权利要求可达数千字符，化学/生物领域更长；且嵌套 claim-text 展平后拼接 |
| `description_section.section_text` | `TEXT` | `LONGTEXT` | 说明书全文是最大文本域（单篇可达数百 KB），必须 LOB 类型 |
| `non_patent_citation.npl_biblio` | `TEXT` | `LONGTEXT` | 引用字符串格式不固定，宁长勿断 |
| `title.title_text` | `VARCHAR(2000)` | `VARCHAR(2000)` | 标题可控长，定长上限更利于索引/约束 |
| `patent.appln_nr_original`、`*.event_text`、`*.npl_title` 等 | `VARCHAR(n)` | 同 | 有明确业务上限 |

> 选型结论：**核心长文本统一用无长度上限的大对象类型**（PostgreSQL `TEXT`，MySQL `LONGTEXT`），不参与 B-Tree 普通索引；如需全文检索，PostgreSQL 建 GIN(tsvector) 或 MySQL 建 FULLTEXT，本阶段只给出建议，由 B/C 落地。

## 6. 日期、号码与编码策略

1. **日期统一 `DATE` 存储**，同时保留 `*_raw CHAR(8)` 原文：
   - 完整日期 `YYYYMMDD`（如 `20230105`）→ `DATE '2023-01-05'`；
   - **月精度** `YYYYMM00`（如引用文献 `20131200`，XML 解析报告 §3-2）→ `cited_doc_date` 置 NULL，`cited_doc_date_raw` 保留原文；查询需月精度时从 raw 安全解析年/月，不伪造“当月 1 日”。
   - 缺失日期（`9999-12-31` 之类 DOCDB 哨兵值）→ 一律转 NULL，不存哨兵。
2. **专利号/申请号解析**（格式：局代码 + 号码 + 种类码，如 `US 20230000001 A1`；申请号 `US 17/364,781`）：
   - `publication`: `publn_auth`(US) + `publn_nr`(20230000001，去空格/斜杠) + `publn_kind`(A1)；
   - `patent`: `appln_auth` + `appln_nr` + `appln_kind`，`appln_nr_original` 保留原文（`17/364,781`），`appln_nr_epodoc` 存 `US17364781` 便于跨局检索；
   - 引用中的被引文献号同样拆 `cited_country`/`cited_doc_number`/`cited_doc_kind`（样例 `US 8607677 B2`）。
3. **编码**：XML 声明为 UTF-8；入库连接统一 utf8mb4（MySQL）/ UTF8（PostgreSQL）；导入前用 `&amp;` 等实体解码（Python `ElementTree` 自动处理），参数字面量禁止字符串拼接。
4. **布尔/标志**：统一 `CHAR(1)` 存 `'Y'/'N'`，与 DOCDB 一致，便于跨库迁移。
