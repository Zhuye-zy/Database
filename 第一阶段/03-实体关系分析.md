## 1. 教材设计原则的检查（教材 4.2，p.82–84）

| 原则（教材节号） | 本项目的落实 | 典型“错误设计→最终设计” |
|---|---|---|
| **忠实性** 4.2.1 | 实体/联系与数据手册字段一一对应（INID/XML 路径可追溯，见 02 §4/§8） | 未引入数据中不存在的概念（如“专利价值”），分析结果由视图/临时表生成 |

## 3. 从 E/R 图到关系模式的转换（教材 4.4/4.6）

### 3.1 转换规则汇总（教材 4.4.1–4.4.4）

1. **强实体集 → 关系**（4.4.1）：属性为列，键为主键；复合键保留（如 `classification(scheme_code,symbol)`）。
2. **联系集 → 关系**（4.4.2）：M:N 或含多端键的联系独立成关系，键=各端键的组合+（如有）序属性；多对一/一对一可并入多端（4.4.3）。
3. **关系组合**（4.4.3）：多对一联系并入多端，避免额外连接（本设计将 dataset/country/语言/类型等标注并入业务表）。
4. **弱实体集**（4.4.4）：关系=属主键+部分键+自身属性；本实现用代理键并保留“属主键+部分键”为唯一约束，等价且便于被其它表引用。
5. **ISA 子类**（4.6.1，E/R 方式）：超类关系 + 每个子类关系（主键=超类键+子类属性）。
6. **多路联系**（4.1.10）：本项目未出现独立三元及以上联系；`patent_classification` 的“体系”通过 `classification` 实体表达为两个二元联系（申请-分类号、体系-分类号），符合 4.1.10 的转换思想。

#### 4.2.1 43 个关系的逐表范式覆盖

BCNF 的判定不是“表有主键即满足”，而是检查每个非平凡 FD `X→Y` 的决定因子 X 是否为超键。对数据字典逐表归纳后，完整覆盖如下：

| FD 形式 | 关系（共 43 张，每张恰好出现一次） | 判定 |
|---|---|---|
| 单一自然/代理主键 `K→全属性`，无其他非平凡 FD | `country_office`, `language`, `application_type`, `classification_scheme`, `citation_category`, `ipc_techn_field`, `person`, `natural_person`, `organization` | K 为候选键，BCNF |
| 代理主键 K 与一个业务唯一键 U 均决定全属性 | `dataset`, `keyword`, `patent`, `publication`, `title`, `abstract`, `description_section`, `drawing`, `claim`, `patent_classification`, `patent_citation`, `non_patent_citation`, `patent_family`, `patent_family_member`, `family_member_application_ref`, `family_member_publication_ref`, `family_abstract`, `priority_claim`, `related_application`, `international_application`, `legal_status_event` | K 和 U 都是候选键，BCNF；U 的完整列组合已在本文 §3.2 预览和 `02-实体与属性清单.md` 逐表明细中声明为 UNIQUE |
| 复合自然键 K 决定全属性 | `kind_code`, `legal_event_code`, `classification`, `claim_dependency`, `patent_applicant`, `patent_inventor`, `patent_assignee`, `patent_agent`, `patent_examiner`, `patent_citation_category`, `designated_state`, `patent_keyword`, `family_citation` | 检查过真子集闭包不覆盖全属性，K 最小，BCNF |

因此 43 表均至少在 BCNF，从而必然在 3NF。这个结论仅针对表内 FD；族级聚合列的跨表同步风险仍在 §4.5 单独披露，不用“BCNF”掩盖该工程约束。

### 4.3 两个典型分解（教材 3.3.3/3.3.4 + 3.4.2/3.4.4）

**例 1：文献种类描述的传递依赖**
- 设未规范化关系 `publication0(publication_id, publn_auth, publn_nr, publn_kind, kind_description, publn_date, patent_id, …)`。
- FD：`publication_id → 全属性`；`(publn_auth, publn_kind) → kind_description`。
- `(publn_auth, publn_kind)` 不是 `publication0` 的超键 ⇒ **违反 BCNF**（教材 3.3.3）。
- 分解（教材 3.3.4）：`publication(publication_id, publn_auth, publn_nr, publn_kind, …)` + `kind_code(publn_auth, kind_code, kind_description, …)`。
- **无损连接（chase，3.4.2）**：两关系公共属性为 `(publn_auth, publn_kind)`，它是 `kind_code` 的键 ⇒ 连接可还原全部元组；
- **依赖保持（3.4.4）**：`(publn_auth, publn_kind) → kind_description` 由 `kind_code` 强制保留。

**例 2：分类号分量的部分/传递依赖**
- 设 `patent_classification0(pc_id, patent_id, scheme_code, symbol, section, class_no, subclass, main_group, subgroup, position, value, …)`。
- FD：`pc_id → 全属性`；`(scheme_code, symbol) → section, class_no, subclass, main_group, subgroup`。
- `(scheme_code, symbol)` 不是超键 ⇒ 违反 BCNF；且对候选键 `(patent_id, scheme_code, symbol, source_type)` 而言，分量对 `(scheme_code, symbol)` 存在**部分依赖**，违反 2NF/3NF。
- 分解：`classification(scheme_code, symbol, section, class_no, subclass, main_group, subgroup, version_date, edition)` + `patent_classification(pc_id, patent_id, scheme_code, symbol, position, value, source_type, …)`（方案即最终 43 表之一）。
- 无损连接：公共属性 `(scheme_code, symbol)` 是 `classification` 的键；依赖保持：分量 FD 在 `classification` 内。

**属性闭包演算示例（教材 3.2）**：对 `classification` 取 `X = {scheme_code, symbol}`，闭包 `X⁺` 依次包含 `section, class_no, subclass, main_group, subgroup, version_date, edition, symbol_title`，即 X 是**候选键**；去掉任一属性后闭包不再覆盖全属性 ⇒ 候选键最小。

### 4.4 多值依赖与 4NF 检查（教材 3.6）

- **反例（独立多值属性合并的后果，3.6.1/3.6.4）**：若把专利的“申请人”和“分类号”放在一个关系
  `patent_person_class(patent_id, person_id, scheme_code, symbol)`，则存在多值依赖
  `patent_id ↠ person_id` 与 `patent_id ↠ scheme_code`，且二者**相互独立**（申请人集合与分类号集合互不影响），
  该关系不属于 4NF，会出现教材所述的“独立多值属性冗余”。
  分解（3.6.5）：`patent_applicant(patent_id, person_id, …)` + `patent_classification(patent_id, scheme_code, symbol, …)`，本设计正是如此。
- **正向结论**：`claim(publication_id, lang_code, claim_number, claim_text)` 中，
  `(publication_id, lang_code, claim_number) → claim_text` 把同一（申请、语言、编号）的文本唯一确定，
  从而阻断了 `publication_id ↠ lang_code`：交换两元组的语言会改变函数依赖右侧值，新元组不在关系中 ⇒ 不存在该 MVD。
  因此 `claim` 满足 4NF（其余多语言表 `title`/`abstract` 同理）。
- **范式关系（3.6.6）**：4NF ⊂ BCNF ⊂ 3NF；本项目要求 3NF（课程），实际设计达到 BCNF/4NF。
- **原始溯源列边界**：`legal_status_event.designated_states_raw` 仅保存源数据对账文本，不将其解释为可查询的多值关系；指定国的关系语义只由 `designated_state` 的多行表达。

| 派生列 | `filing_year`、`granted`、各类计数一律不落列，由视图/生成列提供（见 §7） |

## 5. 关键建模决策（按教材概念重述）

1. **引用（R29/R45）**：`patent_citation` 保留引用方/被引方两个 patent 外键，并新增不可空 `citing_publication_id` 标识引用实际出现在哪份文献；被引方可在库外，此时保留外部标识并令解析外键为空。B 必须校验源 publication 所属 patent 与 `citing_patent_id` 一致。
2. **专利族（R31/R41–R44）**：DOCDB 的 family-member 是族内弱实体，不等同于一行本地 patent。成员的多格式申请号、多份公布号、族级摘要分别落三个子表；只有匹配成功时才回填 `member_patent_id`。这避免上一版每成员只存一个公布号的丢数。
3. **从属权利要求（R22）**：一元 M:N + 角色（从属/被依赖）+ 描述属性（依赖类型、引用原文），独立关系 `claim_dependency`；两端须同属一份 `publication`（复合校验）。
4. **弱实体集与代理键**：教材 4.4.4 的关系键为“属主键+部分键”；实现层加代理键 `*_id`，但把该组合设为 UNIQUE（如 `claim(publication_id, lang_code, claim_number)`），保持教材语义与实现性能。
5. **ISA 与角色正交**：`person` 的子类（自然人/机构）与角色关联表互不干扰；查询“某机构作为申请人的专利”经 `patent_applicant` 即可。
6. **非专利引用（R30）**：作为 1:1 扩展关系；若要严格二元化，可再拆 “引用-专利” 与 “引用-非专利” 两个联系集——当前选择在 03 §4 说明并列入 91 待议。

## 6. 对 B 阶段的影响（结合教材第7章约束机制）

1. **建表顺序（教材 4.4 转换顺序）**：维表 → `patent` → `publication` → 文献弱实体 → `person` 与 ISA 子类 → 角色/分类/引用 → `patent_family` → `patent_family_member` → 两个成员号码子表与 `family_abstract` → 优先权/事件/关键词。
2. **键与外键（教材 7.1）**：43 张表全部声明主键；复合外键至少包括 `(publn_auth,publn_kind)→kind_code`、`(scheme_code,symbol)→classification`、`(event_auth,event_code)→legal_event_code`。预览表现已包含 `PK/FK` 列，不再漏列关联表外键。
3. **CHECK/触发器等（教材 7.2/7.4/7.5，加分项）**：
   - CHECK：`publn_date >= patent.appln_filing_date` 跨表无法用 CHECK，需触发器或断言；`claim_dependency` 两端同文献、`cited_*` 与 `cited_patent_id` 互斥等用触发器校验；
   - 建议触发器：维护 `patent_family` 成员计数/防自引用环（引用/优先权/关联申请形成环时报警）。
4. **ISA 影响**：所有角色关联表仍只引用超类 `person`；`natural_person`/`organization` 的插入必须在 `person` 之后（先超类后子类，教材 4.6.1）。
5. **弱实体集影响**：弱实体集表的删除应级联（`ON DELETE CASCADE`）；插入必须先有属主。
6. **规范化结论**：在文档声明的业务 FD 下，43 张表逐表均满足 BCNF（从而满足 3NF）；三个 DOCDB 族子表把独立多值分开，消除了上一版的重复组/丢值风险。
